## 1. Step 0: scope challenge

**What already exists**
- `requireAuth` (admin JWT, sliding refresh, `role === 'admin'` check). It is reused unchanged. The JWT carries `id` = `User._id`.
- The `User` model (admin logins). It is referenced, not modified (D8).
- `services/llm/router.ts` `complete()`, `ModelTier`, `ToolKey`, `DEFAULT_CONFIG`, stub fallback; `lib/anthropic.ts`; `services/llm/cost.ts` `calculateCostMicroUsd`. All reused; only the `ToolKey` union and `DEFAULT_CONFIG` gain entries.
- The atomic counter pattern from `models/Invoice.ts` (`$inc` with an E11000 retry). The pattern is copied, but the model is not shared, so SalesOS does not import invoice code.
- `__tests__/helpers/testEnv.ts` (mongodb-memory-server) and the `invoices-routes.test.ts` pattern (build a bare express app and mount the router).

**Minimum set of changes.** These are the record store (D7), membership and roles (D8), the lease (D10), bootstrap and the setup script (D11, D15), and the AI endpoints (D17). No per-entity endpoints: the prototype's ~99 actions stay client-side (D7).

**Complexity check.** This touches more than 8 files and adds more than 2 services, so the check triggers. That is justified here, because each service maps to one binding decision and each one is small. The merge and access logic are **pure modules** (no I/O) so they can be unit tested exhaustively. The I/O services stay thin.

**Stack pattern check**
- Express 4 does not catch rejected promises from async handlers, and this repo has no `asyncHandler` or error middleware. SalesOS adds a 6-line `asyncRoute` wrapper and a **router-level** error handler, so nothing leaks into other routers.
- The global `app.use(express.json())` has a 100 kB limit, which is too small for a 500-op batch. The `/sales` router therefore has to be mounted **before** the global parser, with its own `express.json({ limit: '2mb' })` (the same ordering trick as the Stripe webhook).
- No validation library exists in the repo, and adding one is a new dependency. Validation is written as hand-rolled type guards in `services/sales/validate.ts`. URL fields are checked by `services/sales/url.ts` (`urlProblem`, `assertUrlField`), driven by `urlFields` on the collection spec (see 3.5 and contract 5.1).
- Mongoose `Mixed` drops empty objects unless `minimize: false` is set. The `SalesRecord` schema sets `minimize: false`.

**Unit testability.** `merge.ts`, `access.ts`, `scope.ts`, `classifyRules.ts`, `aiParse.ts` and `context.ts` are pure functions. The routes are tested over supertest against the memory server.

## 2. Architecture

```
Browser (/admin/sales chunk, ported store)
  │  diff store on commit → ops[] with baseRev (+ items/paths for merge fields)
  │  poll every 15s with cursor
  │  engine tick → separate batch with engine:{sessionId,businessIds}
  ▼
/sales router  (mounted before global json parser; express.json 2mb)
  requireAuth ──► requireSalesMember (loads SalesMember fresh every request)
  ├─ GET  /me, /bootstrap, /records/changes, /members     (read: scope filter)
  ├─ POST /records/batch                                   (write: access → merge → CAS write)
  ├─ POST /engine/lease, /engine/lease/release             (per-business lease)
  ├─ POST /demo/wipe
  └─ POST /ai/*  ──► services/sales/ai ──► services/llm/router.complete() ──► Anthropic | stub
                                      └─► sales_ai_usage ($inc, fire-and-forget)
services/sales/
  access.ts (pure)  scope.ts (pure)  merge.ts (pure)  validate.ts (pure)
  records.ts  members.ts  lease.ts  bootstrap.ts  errors.ts
models/sales/
  SalesMember  SalesRecord  SalesEngineLease  SalesCounter  SalesAiUsage
Mongo (main DB "status-dashboard"): sales_members, sales_records, sales_engine_leases,
  sales_counters, sales_ai_usage
```

**How a write flows (one op inside a batch)**
```
op ─► validate shape ─► load current doc (collection,id)
   ─► access.check(member, op, current)            403 FORBIDDEN / ROLE_REQUIRED
   ─► merge.apply(current, op)  → {patch, conflicts, applied}
   ─► if patch empty and no conflicts → noop
   ─► seq = SalesCounter.$inc('salesSeq')
   ─► findOneAndUpdate({_id, rev: current.rev}, patch + rev+1 + seq)   (CAS)
        └─ no match → reload and re-merge (max 3 tries) → CONTENTION
   ─► side effects: recompute company/contact scope (rels), cascade privateTo to messages (threads)
   ─► result {status: applied|merged|noop|conflict|rejected, rev, record}
```

**Dependency direction.** routes → services → models. Services never import `express` and throw a `SalesError(code, status, details)`, which the router-level handler maps to HTTP.

### 3.2 `SalesMember` (`models/sales/SalesMember.ts`, collection `sales_members`)

```ts
export interface ISalesMember {
  _id: Types.ObjectId
  userId: Types.ObjectId            // ref 'User' (admin login). One member per login.
  super: boolean                    // D15: admin rights in every business
  roles: Map<BusinessId, Role>      // per-business role; keys validated against BUSINESS_IDS

  title: string                     // profile fields the prototype renders
  color: string                     // '#RRGGBB'

  updatedBy: Types.ObjectId | null

```
- Schema: `{ timestamps: true, collection: 'sales_members' }`. `roles` is `{ type: Map, of: { type: String, enum: ROLES }, default: {} }`, and a pre-validate hook rejects keys that are not in `BUSINESS_IDS`.
- Index: `{ userId: 1 }` unique.
- **Why a reference to User, not embedded:** User is shared with the rest of the admin area (D3). Display name, username and email are read from `User` when the members list is built, using one `$in` query (no N+1).

### 3.3 `SalesRecord` (`models/sales/SalesRecord.ts`, collection `sales_records`)

```ts
export interface ISalesRecord {
  _id: Types.ObjectId
  collection: CollectionName        // stored as `coll` in Mongo: `collection` is reserved in Mongoose
  id: string                        // client id, e.g. 'dl_k3x9…'; unique per collection
  data: Record<string, unknown>     // the prototype record, verbatim (Mixed, minimize:false)
  rev: number                       // per-record revision, 1 on create, +1 per applied write
  seq: number                       // global change sequence (sync cursor), from SalesCounter
  fieldRevs: Map<string, number>    // path → rev at which that path last changed (merge, D16)
  scopeBiz: string[]                // businesses whose members may read it; [] = global
  privateTo: string[] | null        // member userIds; when set, only they may read (no super bypass)
  deleted: boolean                  // tombstone
  deletedAt: Date | null
  deletedBy: string | null
  demo: boolean                     // D11 demo load/wipe marker
  createdBy: string                 // member userId (hex) — the trusted actor, not data.actorId
  updatedBy: string
  createdAt: Date; updatedAt: Date
}
```
- Mongoose reserves the path name `collection` (it clashes with `Document.prototype.collection`), so the schema field is **`coll`** and there is no alias. The serializer maps `coll` to `collection` in the wire shape.
- Options: `{ timestamps: true, minimize: false, collection: 'sales_records', versionKey: false }`.
- **`fieldRevs` path keys:** a top-level field is `deal`-style `stageId`. An item in a keyed list is `notes#<itemId>`. A key in a per-key object is `fields/<key>`. Field names, item ids and object keys are validated against `^[A-Za-z0-9_-]{1,80}$`, so none of them can contain `.` or `$` (Mongo Map key rules).
- **Why `Mixed` for `data`:** D7 is a generic store on purpose. Shape is validated in the service (`validate.ts`): a plain JSON object, ≤ 256 KB serialised, depth ≤ 12, no key starting with `$` or containing `.`, `data.id === id`, plus the per-collection required keys in 3.5.

**Indexes**

| Index | Options | Serves |
|---|---|---|
| `{ coll: 1, id: 1 }` | unique | every get, put and delete |
| `{ seq: 1 }` | | changes feed (`seq > cursor`) |
| `{ updatedAt: 1 }` | | changes feed overlap window (5.4) |
| `{ scopeBiz: 1, coll: 1, deleted: 1 }` | | bootstrap and list by collection in scope |
| `{ coll: 1, 'data.companyId': 1 }` | partial `{ coll: 'companyRels' }` | recompute company scope |
| `{ coll: 1, 'data.contactId': 1 }` | partial `{ coll: 'contactRels' }` | recompute contact scope |
| `{ coll: 1, 'data.threadId': 1 }` | partial `{ coll: 'messages' }` | cascade thread privacy to messages; AI reply-suggest |
| `{ coll: 1, 'data.enrolmentId': 1, 'data.stepId': 1 }` | partial `{ coll: 'messages' }` | duplicate-send guard |
| `{ demo: 1 }` | partial `{ demo: true }` | demo wipe |

Expected size: internal sales data for four small teams, which means tens of thousands of records, not millions. All indexes are built on an empty, new collection, so no deployment window is needed.

**Query plan check**
- Bootstrap: `{ scopeBiz: { $in: myBiz } ∪ scopeBiz: [], deleted: false }` uses the `scopeBiz` index (multikey). The `privateTo` check is applied in code, because it is a small filter.
- Feed: `{ seq: { $gt: s } }` uses `seq_1`, and `{ seq: { $lte: s }, updatedAt: { $gte: t - 30s } }` uses `updatedAt_1`. Results are scope-filtered in code, because the `$or` of scope makes compound indexes awkward and the result set per poll is small.

## 4. Access control (D8 role matrix, enforced server-side)

### 4.1 Effective role
```ts
effectiveRole(member, b): EffectiveRole | null =
  member.super ? 'super' : member.roles.get(b) ?? null
rank = { viewer: 1, sales: 2, manager: 3, admin: 4, super: 5 }
canRead(m,b)   = rank ≥ 1      canEdit(m,b)  = rank ≥ 2
canManage(m,b) = rank ≥ 3      canAdmin(m,b) = rank ≥ 4
readable(m)    = super ? BUSINESS_IDS : [...m.roles.keys()]
```
This is the matrix from the decision log. **viewer** can read only, **sales** can create and edit records, **manager** can also manage team data, **admin** can also change admin settings, and **super** has all of that in every business.

### 4.2 Read rule (every read path: bootstrap, list, get, changes, AI context loading)
```
visible(rec, m) =
  !blockedByReadTier(rec.collection, m)
  && (rec.scopeBiz.length === 0 || rec.scopeBiz.some(b => readable(m).includes(b)))
  && (rec.privateTo === null || rec.privateTo.includes(m.userId))
```
- `privateTo` has **no super bypass**, which matches the prototype (`Q.threadBody`, `Q.actVisible`) and D8 ("restricts private mailbox threads to their owner").
- **Note-level filter:** `notes[]` items on companies, contacts and deals carry `businessId` and `visibility`. On read, items are dropped when `businessId` is not readable, or when `visibility === 'private'` and `by !== me`. This is safe with the keyed merge: hidden items are never in the client's base, so they are never treated as deleted.

### 4.3 Write rule
For each op the order is:
1. Collection is known, and not `users`. Otherwise `UNKNOWN_COLLECTION` or `READ_ONLY`.
2. The target business set is the existing `scopeBiz` for an update or delete, or the scope computed from the new data for a create (for `viaRels`, see 4.4).
3. Tier check: `canTier(m, b, spec.writeTier)` must hold for **at least one** b in the target set, except company and contact delete, which need **all**. Otherwise `ROLE_REQUIRED` with `details: { needed, businessId }`.
4. Owner fields: on update, if any `ownerFields` path changes and the caller is not `canManage` in the record's business, reject with `ROLE_REQUIRED` (`needed: 'manager'`). The exception is `tasks.assigneeId`, when the current assignee is the caller. On create, owner fields are free, because the engine creates tasks assigned to other users.
5. Append-only: an update or delete on `activities` or `audit` gives `APPEND_ONLY`. A put that repeats identical data is a `noop`, so client retries stay safe.
6. Special cases from the table: global suppressions, settings ids, notifications recipient, savedViews owner.
7. `demo: true` on create needs `canAdmin` in the record's business. Global records need super.

### 4.4 Companies and contacts (shared across businesses)
- `scopeBiz` = the distinct `businessId` of non-deleted `companyRels` with `data.companyId === id` (likewise `contactRels`/`contactId`). It is recomputed after every rel create, delete or resurrect. If it changes, the company's `scopeBiz` is updated and it gets a **new seq**, so members of the newly linked business receive it on their next poll.
- **Create authorisation:** a new company or contact must be accompanied **in the same batch** by a rel put for it in a business where the caller `canEdit`. The batch is pre-scanned for this. Otherwise `ROLE_REQUIRED` with `details.reason = 'no_relationship'`.
- An orphan company (all rels deleted) has `scopeBiz: []`. That would make it global, so **for `viaRels` collections an empty scope means super-only**, not global.

### 4.5 Integrity guards
- **Duplicate-send guard (D10 second line):** a `messages` create with `status: 'sent'` is rejected as `DUPLICATE_SEND` when a non-deleted message with the same `enrolmentId` and `stepId` already has `status: 'sent'`.
- **Engine batches:** when `engine` is present on a batch, every op's business must be leased by `engine.sessionId` (unexpired) **before any op is applied**. Otherwise the whole batch gets `409 LEASE_LOST` and nothing is written.

## 5. Revisions, merge and sync (D7 and D16)

### 5.1 Op shapes
```ts
type Path = string   // 'stageId' | 'fields/decisionDate'  (object-map key only for declared objectMaps)

interface PutOp {
  op: 'put'
  collection: CollectionName
  id: string
  baseRev: number | null          // null or 0 = create
  set: Record<Path, unknown>      // create: the full record (top-level keys); update: changed paths only
  unset?: Path[]                  // paths removed from the record
  items?: Record<string, {        // keyed lists only (e.g. 'notes')
    upsert?: Array<{ id: string } & Record<string, unknown>>
    remove?: string[]
  }>
  demo?: boolean                  // create only (D11)
  resurrect?: boolean             // explicit "keep mine" after a 'deleted' conflict
}
interface DeleteOp { op: 'delete'; collection: CollectionName; id: string; baseRev: number }
type Op = PutOp | DeleteOp
```
On create, `set` must contain the full record including `id`, and the keyed lists go in `set` as whole arrays. On update the client sends only changed paths. The client already keeps its original copy (D16), so it diffs top-level keys, per-key for `objectMaps`, and per-item for `keyedLists`.

### 5.2 Merge algorithm (`services/sales/merge.ts`, pure)
```
input: current {data, rev, fieldRevs, deleted}, op, nextRev
create (baseRev null/0):
  no doc                         → applied (rev 1, every path fieldRev 1)
  doc, not deleted, data deepEqual set   → noop  (idempotent retry)
  doc, not deleted, different    → conflict kind 'exists'
  doc deleted                    → conflict kind 'deleted' (unless resurrect)
update:
  no doc                         → rejected NOT_FOUND
  deleted && !resurrect          → conflict kind 'deleted', current: null
  for each path p in set ∪ unset:
     clean   if fieldRevs[p] ?? 0 ≤ baseRev
     same    if deepEqual(current(p), mine(p))           → nothing to do (convergent)
     else    → conflict {path:p, mine, theirs}
  for each keyed list L, item i:
     upsert i: k = L#i.id; clean if fieldRevs[k] ≤ baseRev or deepEqual; else conflict
               (absent on server and fieldRevs[k] > baseRev ⇒ deleted by someone else ⇒ conflict, theirsDeleted:true)
     remove i: absent ⇒ noop; fieldRevs[k] > baseRev and changed ⇒ conflict; else remove
  apply every clean path, bump fieldRevs of applied paths to nextRev
  status = conflicts ? 'conflict' : (baseRev < current.rev ? 'merged' : 'applied')
delete:
  no doc or already deleted      → noop
  any fieldRev > baseRev         → conflict kind 'modified' (edited since you loaded it)
  else                           → tombstone (deleted:true, data kept for audit, rev+1)
```
**Partial apply:** clean paths are written even when other paths in the same op clash. The conflict result returns the **new** `rev`, so "keep mine" is simply a resend of the clashing paths with `baseRev = conflict.rev`, and "keep theirs" sends nothing. Keyed-list ordering: the server keeps the current order, inserts new items at the front (the prototype uses `unshift`), and applies removals by id.

### 5.3 CAS write
`findOneAndUpdate({ _id, rev: current.rev }, { $set: {...paths as 'data.<p>' or 'data.fields.<k>', rev, seq, updatedAt, updatedBy, 'fieldRevs.<k>': nextRev }, $unset: {...} })`. If it returns null, someone else wrote in between: reload and re-merge, up to 3 attempts, then return `rejected` with `CONTENTION` (the client retries on the next commit). A create uses `create()`, and E11000 means a concurrent create, which is then re-merged as an update with `baseRev: null` (the `exists`/`noop` path).

### 5.4 Change feed and cursor
- `seq` comes from `SalesCounter` (`_id: 'salesSeq'`, `$inc`) for every write, scope cascade and tombstone.
- **Late-commit hole:** seq is allocated before the record write commits, so a poller can see seq 11 before seq 10 lands. The cursor therefore carries time as well: `cursor = base64url(JSON { s: lastSeq, t: serverMsAtPollStart })`. The query is:
  `{ seq: { $gt: s } } ∪ { seq: { $lte: s }, updatedAt: { $gte: new Date(t - 30_000) } }`, sorted by `seq`, limited to 1000.
  The overlap branch re-sends a few recent records. The client ignores anything with `rev ≤` the rev it already holds.
- Pagination: when more than `limit` rows match, return `more: true`, with `s` set to the last seq returned and `t` unchanged. The client calls again immediately.
- **Redaction:** a record that is in the feed window and in the caller's business scope but fails `privateTo` (for example a thread just made private) is emitted as `{ collection, id, rev, hidden: true, deleted: true, data: null }`, so the client drops it. A company that left the caller's scope is not detected. That is acceptable, because company data is not private between businesses (4.4).
- **Members:** each feed response includes `membersVersion` (the max `SalesMember.updatedAt` as ISO plus the count). When it changes, the client refetches `/sales/members` and `/sales/me`.

### 6.1 Mounting
`src/index.ts`: `app.use('/sales', salesRouter)` is placed **before** `app.use(express.json())`. ### 6.2 Error envelope
The repo convention is `{ error: string }`, and the website `apiFetch` reads `body.error`. SalesOS extends it as follows:
```ts

type SalesErrorCode =

```
401 and 403 from `requireAuth` keep their existing `{ error }` shape (no `code`); the web treats a code-less 403 as no access. Conflicts are never an HTTP status: they are `OpResult.status: 'conflict'` inside a 200 batch response. ### 8.2 `scripts/sales-setup.ts` (`npm run sales-setup -- <username> [<username>…] [--dry-run]`)
1. Connect with `mongoose.connect(MONGODB_URI, { dbName: 'status-dashboard' })`, as `create-admin.ts` does.
2. | Codepath | What can fail | Error | Rescue | User sees |
|---|---|---|---|---|
| requireSalesMember | No SalesMember / inactive | NOT_A_MEMBER / MEMBER_INACTIVE 403 | none | "Ask an admin to add you to SalesOS" |
| requireSalesMember | `req.user.id` missing or not ObjectId (old token) | NOT_A_MEMBER 403 | none | same; re-login fixes |
| any route | Mongo unreachable | MongooseError | router error handler → 500 INTERNAL, logged with route + member id | "Couldn't reach the server, retrying"; client keeps local edits queued |
| body parser | > 2 MB | `entity.too.large` | 413 PAYLOAD_TOO_LARGE | client splits batch |
| batch | > 500 ops | BATCH_TOO_LARGE 413 | client chunks at 200 | invisible |
| put (create or update) | `companies.website`/`linkedin`, `contacts.linkedin` not empty and not an http(s) URL (also `javascript:`, `data:`, credentials, whitespace, > 2048 chars) | INVALID_URL per op, `details: { path, reason }` | checked before any read-modify-write; nothing written, other ops continue | inline field error / "Couldn't save" |
| put | concurrent writer between read and CAS | CAS miss | re-merge ×3, then CONTENTION per op | invisible; resent on next commit |
| put | same path changed by both | conflict | partial apply + conflict result | Keep mine / keep theirs prompt (D16) |
| put | record deleted by someone else | conflict 'deleted' | report, require `resurrect` | "This was deleted by X. Restore it?" |
| put create | network retry of a create that succeeded | E11000 / exists | deepEqual → noop | invisible |
| rel write | company scope recompute fails after rel saved | MongooseError | logged `[sales] scope recompute failed` with ids; next rel write or `ensureScope` on read of that company repairs | other business may not see the company until repaired |
| thread privacy change | message cascade fails | MongooseError | logged; thread result still returned; messages fixed on next thread write | messages may stay visible briefly; logged as error |
| engine batch | lease expired mid-run | LEASE_LOST 409 | nothing applied; client stops engine and reacquires | invisible; engine resumes when lease re-held |
| messages create | step already sent | DUPLICATE_SEND (op rejected) | client drops local duplicate | invisible |
| lease acquire | held by other | E11000 | report holder | Demo Control Centre shows "Sequences are being run by <name>" |
| members PATCH | would remove last super | LAST_SUPER 409 | none | "SalesOS needs at least one super user" |

| AI any | no API key | stub result | mode 'stub' (classify → regex) | "AI not configured" badge + template |

| AI usage $inc | Mongo error | MongooseError | `.catch` logs `[sales.ai] usage increment failed` | invisible |

No silent catches: each `catch` either rethrows with context, logs with ids, or converts to a typed result.

## 11. Observability

- Prefix `[sales]` and `[sales.ai]`. No record data or prompt text in logs. Log only ids, collection names, codes, counts and timings.
- `info`: member added or changed (actor, target, changed keys), lease acquired or taken over (business, from user, to user), demo wipe (actor, count), bootstrap inserted N records at startup.
- `warn`: CONTENTION after 3 tries (collection, id), LEASE_LOST (session, businesses), DUPLICATE_SEND (enrolmentId, stepId), AI fallback (tool, reason).
- `error`: every 500 (route, member userId, error message, stack), scope recompute or cascade failures (ids), AI provider errors (tool, model, latency, provider message), usage increment failure.
- Each AI call logs one line: `{tool, mode, model, latencyMs, tokensIn, tokensOut, microUsd}`.
- The `/health` response is unchanged.

## 13. Performance

- Bootstrap is O(records in scope). At the expected scale (≤ 50k records) that is one indexed query plus `.lean()`, and the response is a few MB at worst. Responses are gzipped only if compression is added (it is not in the repo today, and is not added here).
- Batch: per op that means 1 read, 1 counter `$inc` and 1 CAS write. For 200 ops that is about 600 round trips. That is acceptable for Phase 1 and the client chunks at 200. The rel-scope recompute adds 1 query per rel op.
- No N+1: the members list joins `User` with one `$in`. AI context loaders fetch by `$in` per collection.
- Poll every 15 s per open tab: each poll does 2 indexed range queries. That is negligible at team size.
- `fieldRevs` grows with keyed-list items. It is bounded by the notes per record, which is small.
