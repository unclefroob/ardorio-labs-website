## 2. Transport, auth, envelope

- Base: `${VITE_API_URL}/sales`. JSON only. `Content-Type: application/json`.
- Auth: `Authorization: Bearer <admin JWT>` (the existing `ardorio_admin_token`). The existing sliding refresh applies: when the response has `X-Refreshed-Token`, the client stores it (CORS already exposes it).
- The `/sales` router is mounted after `cors()` and **before** the global `express.json()`, with its own `express.json({ limit: '2mb' })`.
- Middleware order: `express.json(2mb)` → `requireAuth` → `requireSalesMember` → routes → `salesErrorHandler`.
- Error body for every non-2xx produced by the sales router:

```ts
export interface SalesErrorBody {
  error: string                       // human message, safe to show
  code: SalesErrorCode
  details?: Record<string, unknown>
}
```

`requireAuth` runs first and keeps its existing bodies, which have **no `code`**: `401 { error: 'Unauthorized' | 'Invalid or expired token' }`, `403 { error: 'Forbidden' }` (token is not an admin token). The web client treats a 403 with no `code` like `NOT_A_MEMBER`.

The web client does NOT use `apiFetch` for `/sales` (it discards status and body). `src/sales/api/http.ts` is a sales wrapper that reuses `API_BASE`/`TOKEN_KEY`, the refreshed-token handling and the 401 redirect, and on non-2xx throws `SalesHttpError { status: number; body: SalesErrorBody | null }`.

Nullability rule: a key typed `T | null` is always present; a key typed `k?: T` may be absent and is never `null`. Dates on the wire are ISO 8601 strings.

### 5.1 Op rules both sides implement

- **No `append` op.** Append-only collections (`activities`, `audit`) are written as `put` with `baseRev: null` (create). An identical re-put is `noop`, so retries are safe. Any update/delete of them is `rejected APPEND_ONLY`.
- **Notes** (`notes` on `companies`, `contacts`, `deals`) are a keyed list: on update the client sends `items.notes.upsert` (new or edited items, whole item) and `items.notes.remove` (ids), never `set.notes`. On create, `set.notes` carries the whole array. Each note item carries at least `id`, `businessId`, `by`; `visibility: 'private'` makes it visible only to `by`. The server inserts new items at the front (prototype `unshift`).
- **Deal custom fields** (`deals.fields`, an object) are diffed per key: `set['fields/<key>']`, `unset: ['fields/<key>']`.
- **Every other array or object field** (e.g. `tags`, `contactIds`, `stageHistory`, `stages`) is one unit (D16): the whole value goes in `set.<key>`; concurrent edits to it clash.
- **baseRev** is the rev of the client's synced copy at the moment of the **earliest** still-unflushed edit to that record. A poll that advances the synced copy while edits are pending does NOT advance their baseRev (otherwise the server would treat a real clash as clean and silently overwrite).
- **Companies / contacts create** must be in the **same batch** as a `companyRels` / `contactRels` create for a business where the caller can edit, else `rejected ROLE_REQUIRED` with `details.reason: 'no_relationship'`. The client chunker never splits an entity create from its rel ops.
- `businessId` (and the rel keys `companyId`/`contactId`) are immutable after create (`IMMUTABLE_FIELD`).
- Required keys per collection are in section 10; missing → `rejected VALIDATION`.
- **Link fields** (`companies.website`, `companies.linkedin`, `contacts.linkedin`; `meetingLink` on the member endpoints) hold user-supplied URLs that the UI renders as anchors. The server accepts only the empty string (or `null`, or the field absent/`unset`) or a URL that: is a string of at most **2048** characters (`meetingLink`: 500); starts with `http://` or `https://` (scheme is case-insensitive); has a non-empty host (Unicode/IDN hosts are fine); contains **no username or password** (`user:pass@host` is rejected); and contains no whitespace, control characters or backslashes anywhere (so a value with leading or trailing spaces is rejected, not trimmed: the server never rewrites a value, and the client must trim before sending). `javascript:`, `data:`, `vbscript:`, `file:`, `mailto:`, `ftp:` and scheme-less strings (`www.example.com`) are rejected. A bad value is `rejected INVALID_URL` with `details: { path: '<field>', reason }`, where `reason` is one of `type | length | characters | scheme | format | credentials`. The check applies to create, to every `set` of that path on update (a merge of a stale `baseRev` is still validated), and to engine batches; an unrelated update to a record is never blocked by a field it does not touch. A rejected URL op changes nothing; other ops in the batch are unaffected. On the member endpoints it is a whole-request `400 INVALID_URL` with the same `details`.
- Limits: max 500 ops per request (`413 BATCH_TOO_LARGE`); the client chunks at **200**. Body ≤ 2 MB (`413 PAYLOAD_TOO_LARGE`, client halves the chunk and retries). `data` ≤ 256 KB serialised, depth ≤ 12, no key starting with `$` or containing `.`, and `set.id === id` on create.
- Ops apply **in order, non-atomically**. Per-op outcomes are always in `results` with HTTP 200, including conflicts and permission rejections. The only whole-request failures are `400 VALIDATION` (malformed body), `413`, `409 LEASE_LOST` (engine batch, nothing applied), `401/403` (auth/membership) and `500 INTERNAL`.

### 5.2 Client handling of each OpResult

| status / code | Meaning | Web client does |
|---|---|---|
| `applied` | written, no one else touched it | set synced copy = `record`, rev = `rev` |
| `merged` | written, merged with others' changes to other paths | set synced copy = `record`; subtle toast "Updated with changes from <name>" |
| `noop` | nothing to change (identical retry, convergent edit, delete of already-deleted) | set synced copy = `record` (or drop if null) |
| `conflict` `field` | clean paths were applied; listed paths kept **theirs** | set synced copy = `record`, roll the clashing paths back locally, prompt **Keep mine / Keep theirs** (D16). Keep mine = resend those paths with `baseRev = result.rev`. Keep theirs = nothing. |
| `conflict` `deleted` | record was deleted by someone else | drop pending ops for it, show "This record was deleted by <name>" banner; optional **Restore** (explicit button, with "Leave deleted") resends the full record with `resurrect: true`. Never auto-recreated (D16). |
| `conflict` `exists` | create of an id that exists with different data | treat as `field` conflict on the differing paths (only realistic after id reuse; logged) |
| `conflict` `modified` | delete of a record edited since baseRev | keep the record, prompt "Changed by <name> since you opened it. Delete anyway?"; yes = resend delete with `baseRev = result.rev` |
| `rejected` `ROLE_REQUIRED` / `READ_ONLY` / `APPEND_ONLY` / `IMMUTABLE_FIELD` / `VALIDATION` / `INVALID_URL` / `UNKNOWN_COLLECTION` | not allowed / malformed | roll back to synced copy, drop op, toast "You don't have permission" (role codes) or "Couldn't save: <message>"; `logSales`. For `INVALID_URL` show the message inline on the field named by `details.path` where the form is still open |
| `rejected` `NOT_FOUND` | update of a record that never existed or is not visible | drop op, remove local record, log |
| `rejected` `DUPLICATE_SEND` | engine sent a step that was already sent | drop op and its local message silently |
| `rejected` `CONTENTION` | 3 CAS misses | keep the op queued; retried on the next flush |

### 5.3 Who wrote what

The server stamps `createdBy`/`updatedBy` from the JWT member; it never trusts `data.actorId` for authorisation.

### 5.4 Read filtering (applies to bootstrap, changes, OpResult.record, AI context)

`visible(rec, member)` = read tier ok && (`scopeBiz` empty and not a `viaRels` collection, or `scopeBiz` ∩ readable businesses ≠ ∅; `viaRels` with empty scope = super only) && (`privateTo` null or includes the member; **no super bypass**). Note items are dropped when their `businessId` is not readable or they are private to someone else.

### 6.1 Bootstrap

```ts
export interface BootstrapResponse {
  me: MeDTO
  users: SalesUserDTO[]
  collections: Record<Exclude<CollectionName, 'users'>, BootstrapRecord[]>  // every key present, [] when none
  settingsDefaults: Record<SettingsId, RecordData>   // virtual defaults for settings ids not yet created (rev 0)
  cursor: string
  serverNow: string
  membersVersion: string
  ai: { enabled: boolean; providers: Record<AiProvider, boolean> }   // enabled = Anthropic key set (unchanged); providers.xai = XAI_API_KEY set (D18, additive). false ⇒ show that provider's "not configured" badge before any call
}
```

- The web Shell calls **R1 once** (it includes `me`; there is no separate initial `/sales/me` call). 403 → designed no-access state ("Ask an admin to add you to SalesOS"); 401 → existing login redirect; network/5xx → retry panel.
- All readable businesses are loaded in one response (D1 portfolio view). There is no `business` query parameter; switching workspace is client-side filtering.
- The server takes `cursor` **before** reading the records (`s` = counter value, `t` = now), so writes landing during the read are re-delivered by the first poll; the client ignores `rev ≤` held.
- A settings id absent from `collections.settings` is read from `settingsDefaults` with rev 0; the client's first save of it is a create (`baseRev: 0`).
- Only non-deleted, visible records, with the note filter applied.

### 6.2 Changes feed (poll)

```ts
export interface ChangesResponse {
  changes: ChangeEntry[]          // sorted by server seq
  cursor: string                  // opaque; store and send back verbatim
  more: boolean                   // true ⇒ call again immediately with the new cursor
  serverNow: string
  membersVersion: string
  clockOffsetMinutes: number      // current settings/clock offset, for the D9 banner
}
```

- Cursor is **opaque** to the client (server encodes `{ s: lastSeq, t: serverMs }` in base64url, with a 30 s overlap window for late commits). The client never builds or edits it. A missing cursor = full resync from 0.
- Poll every 15 s while `document.visibilityState === 'visible'`, immediately after regaining focus/online, and again immediately while `more`.
- Apply rule: ignore an entry with `rev ≤` the held rev. `deleted` or `hidden` → remove the record locally (if it has pending edits, show the deleted banner and drop them). Otherwise replace the synced copy with `data`, then re-apply the record's still-pending local paths on top for display (their baseRev stays as in 5.1).
- `membersVersion` changed → refetch R5 and R4 and replace `users`/`me`.
- The batch response does **not** return a cursor; the poll cursor only advances from R1/R2. Echoes of the client's own writes are skipped by the rev rule.

### 6.3 Engine lease (D10, one lease per business)

```ts
export interface LeaseRequest { sessionId: string; businessIds: BusinessId[] }   // sessionId: crypto.randomUUID() per tab
export interface LeaseInfo {
  businessId: BusinessId
  held: boolean                    // held by THIS session
  expiresAt: string | null         // of whoever holds it; null when nobody does
  holder?: { userId: string; name: string }   // present when another session holds it
}
export interface LeaseResponse { ttlMs: number; renewEveryMs: number; serverNow: string; leases: LeaseInfo[] }  // ttl 45000, renew 15000
export interface LeaseReleaseRequest { sessionId: string }
export interface LeaseReleaseResponse { released: BusinessId[] }
```

- One call acquires or renews. Every SalesOS tab calls R9 every `renewEveryMs` with all businesses where `me.permissions[b].edit`; a non-holder takes over automatically once the holder's lease expires. There is no lease token: `sessionId` is the identity.
- Only businesses with `held: true` are ticked (every 30 s). If R9 fails (network/5xx), treat every lease as not held, stop ticking and show "Automations paused" in the topbar. Never run the engine without a held lease.
- Release on `pagehide`: `fetch(url, { method: 'POST', keepalive: true, headers: { Authorization, 'Content-Type' }, body })`. `navigator.sendBeacon` is **not** used, because it cannot send the Authorization header. Best effort; an unreleased lease expires after 45 s.
- **Engine writes** are flushed in their own batch with `engine: { sessionId, businessIds }` and are never mixed with user ops. The engine tick first flushes pending user ops, then runs, then flushes its ops immediately (no debounce). `409 LEASE_LOST` (`details.businessIds`) means nothing was applied: the client stops the engine for those businesses, rolls the engine's local changes back to the synced copies, and re-acquires; the next holder re-executes the due steps.
- Demo Control Centre shows "Sequences are being run by <holder.name>" from `holder`.

## 7. Clock (D9)

- `settings/clock.data = { offsetMinutes: number }` (integer, |x| ≤ 525600). Writable by admin in any business.
- `serverSkewMs = Date.parse(serverNow) − Date.now()` measured on each R1/R2 response.
- Client `now() = Date.now() + serverSkewMs + offsetMinutes × 60000`. `F.now()`, `F.today()`, the Q selectors and the engine use it.
- Banner "Demo clock: +3d 4h" whenever `offsetMinutes !== 0` (value from the settings record, refreshed by `clockOffsetMinutes` on each poll).
- There is no `settings.demo.clockOffsetMs`. `settings/demo` holds `{ wizaFail, researchFail }` only.

## 8. AI (D17)

All AI goes web → API → `services/sales/ai/provider.ts` → Anthropic via `services/llm/router.ts complete()` (or the router stub), or xAI Grok for `sales.research` (D18, see below). The provider is chosen per tool in one table (`SALES_TOOL_PROVIDERS`); the web never calls a model provider.

**D18 additions (all additive; no route or request shape changes).** Every AI response carries `provider: AiProvider`. `sales.research` runs on Grok (`grok-4.7`, xAI Responses API, `web_search` and `x_search` tools) and returns `inference.sources`. All other tools stay on Claude. With `XAI_API_KEY` unset, research returns `mode: 'stub'`, `provider: 'xai'` and the label "Grok is not configured on the server (XAI_API_KEY unset). Showing the built-in template instead."; other tools are unaffected. A Grok failure is 502 `AI_PROVIDER_ERROR`; malformed output is 502 `AI_BAD_OUTPUT`. Spend is recorded in `SalesAiUsage` (integer micro-USD) with `perProvider` and `perProviderCalls` maps keyed by provider.

## 11. Demo load (D11), client-only

**Superseded (user ruling, 2026-10-09): no demo data.** The Demo page is unregistered from the web app (page registry, route segment, nav) and no loader is built; the notes below are historical and nothing here is implemented. R11 and the `demo` flag remain on the API.

- Skips `businesses`, `users`, `pipelines` and `settings` (the real ones exist and must not be overwritten).
